# Измерения Search B

Измерен поисковый движок на исходном корпусе 899 ID и семи языках. Стенд локальный, без публикации.
Это измерения функций поиска, не времени от ввода до отрисовки будущего экрана C.

Среда: Node v24.19.0, INTEL(R) XEON(R) PLATINUM 8573C; Chromium 154.0.8037.57. Физический Android не проверялся.

## Методика

- Один холодный индекс на язык; 5 прогревочных вызовов и 100 измерений каждого случая в Node / 50 в Chromium.
- Случаи: распространённая фраза, отсутствующее слово, тип+год, фраза+год. P95 берётся из отсортированных фактических измерений.
- Chromium: CDP Emulation.setCPUThrottlingRate с коэффициентами 1 и 6. Это замедление CPU среды, а не калиброванная модель телефона.
- Исходные JSON и метаданные загружены до измерений. Загрузка файлов, отрисовка, RPC и подсветка не включены во время searchIds.
- Память: принудительный GC до/после; в Node отдельно heapUsed, ArrayBuffer и RSS. В Chromium — reported usedJSHeapSize с precise-memory-info. Это не полный RSS приложения.
- Финальный прогон выполнен последовательно, без параллельного запуска тестов. Холодные значения — отдельные замеры, они зависят от нагрузки и JIT.

## Chromium: холодный индекс и повторные запросы

«P95 max» — максимальный P95 среди четырёх измеренных случаев данного языка. Время в миллисекундах.

| Язык | Холодный ×1 | P95 max ×1 | Холодный ×6 | P95 max ×6 | Доп. heap индекса ×6, MiB |
|---|---:|---:|---:|---:|---:|
| RU | 53.5 | 1.00 | 469.8 | 7.40 | 2.11 |
| BE | 13.2 | 0.30 | 115.2 | 2.10 | 0.64 |
| UK | 19.8 | 0.50 | 146.0 | 4.40 | 0.78 |
| HR | 78.8 | 0.70 | 525.3 | 5.50 | 1.75 |
| EN | 68.3 | 0.70 | 459.5 | 5.90 | 1.41 |
| SK | 86.3 | 0.90 | 623.2 | 7.70 | 1.84 |
| LV | 71.8 | 0.70 | 561.6 | 8.10 | 1.63 |

Для повторных запросов задержка мала; холодное построение на замедленном CPU заметно и должно быть вынесено в Worker при интеграции C.
Пять браузерных сценариев проверили Vue-адаптер, все языки через input/select, pending/unknown, пропущенный перевод, точную безопасную подсветку и Worker RPC.
После загрузки корпуса сетевых запросов от поиска и смены языка не было, ошибок страницы нет.

## Node: память

Производный JSON: 907,433 байт; gzip 40,339 байт. Это размер артефакта, не объём всей JS-памяти.
Его отдельный retained heap delta после разбора: 1.53 MiB. Каталог/фасеты: 0.52 MiB heap и 62,632 байт ArrayBuffer.

| Язык | Холодный индекс, мс | P95 max, мс | Доп. heap индекса, MiB | Доп. ArrayBuffer, KiB |
|---|---:|---:|---:|---:|
| RU | 56.86 | 1.075 | 3.04 | 162.9 |
| BE | 11.54 | 0.187 | 1.01 | 24.6 |
| UK | 12.70 | 0.257 | 1.16 | 27.4 |
| HR | 71.96 | 0.615 | 2.35 | 151.4 |
| EN | 65.71 | 1.129 | 1.65 | 206.3 |
| SK | 71.31 | 0.802 | 2.45 | 116.9 |
| LV | 60.65 | 0.487 | 2.19 | 60.4 |

LRU удерживает максимум два поисковых индекса. Эти дельты относятся к одному индексу и исключают уже загруженные тексты, модель, каталог, DOM и отдельный Worker.
Worker дополнительно копирует модель и текущий языковой корпус; его полный heap здесь не измерен. Предыдущий корпус освобождается при loadLanguage, а dispose завершает Worker.
Счётчик payloadBytesLowerBound учитывает нормализованные строки, словарь и postings, но не накладные расходы объектов; он не выдаётся за полный расход памяти.

## Сравнение с нынешним App.vue

Baseline повторяет существующий filter, присутствие выбранного языка и per-record toLocaleLowerCase(). Новому поиску для сравнения задан availability:present.
У нового поиска шире область (контекст), есть Unicode-нормализация и границы полных слов. Отношение скоростей выводится только при побайтно одинаковой последовательности ID.
Если equivalent_result_ids=false, ускорение не вычисляется. Это встречается для фраз UK/SK/LV; различия относятся к контексту/диакритике, не к потерянным ID.

Пример EN при CPU ×6, только совпавшие результаты:

| Случай | ID | Новый P95, мс | Старый P95, мс | Старый / новый |
|---|---:|---:|---:|---:|
| phrase | 856 | 5.900 | 6.200 | 1.05 |
| missing-word | 0 | 0.100 | 6.200 | 62.00 |
| type-year | 9 | 0.100 | 1.200 | 12.00 |
| phrase-year | 17 | 1.200 | 1.300 | 1.08 |

Индекс не быстрее baseline в каждом случае: на небольшом корпусе старый перебор иногда дешевле подготовки списков/проверок. Новая основа обеспечивает более богатую семантику и предсказуемые короткие повторные запросы; общего заявления об ускорении всех случаев нет.

## Worker и пределы вывода

Отдельная проверка настоящего module Worker: холодный запрос EN 78.1 мс; таймер основного потока сработал 24 раз во время ожидания.
Проверены независимые ответы конкурентных RPC, одинаковые ID с синхронным движком и замена активного корпуса. Коэффициент CPU самого Worker не подтверждён: это не Worker-бенчмарк Android ×6.
Синхронный useMessageSearch удобен для интеграционных тестов; для C предпочтителен Worker API с явным состоянием подготовки и отбрасыванием устаревших ответов на стороне UI.

Сырые отчёты: [search-node.json](../reports/stage-b/search-node.json), [search-browser.json](../reports/stage-b/search-browser.json).
Воспроизведение: npm run benchmark:search, затем npm run benchmark:search:browser. Не запускать параллельно с тестами/сборкой.
Главный экран, физический Android, установка PWA и офлайн-поведение этим стендом не проверялись.
